# VPSBox 架构说明

本文面向 VPSBox 的维护者，记录当前代码组织、状态所有权、真实交叉依赖和改动边界。它描述的是现状，不表示脚本已经拆成多个运行时模块。

## 运行与发布形态

- `vpsbox.sh` 是唯一运行时源码及安装发布产物，不依赖仓库中的其他 Shell 文件才能启动。
- 文件被直接执行时，末尾的入口保护才会调用 `vpsbox_main`。被测试 `source` 时不会进入主程序，但仍会执行文件头的 Shell 选项、`umask` 和全局初始化。
- `tests/` 会在加载脚本后按场景替换外部依赖、领域函数和入口。因此，新增顶层副作用、提前缓存函数结果或把共享路径改成只读变量，都可能破坏现有测试方式。
- 单文件形态是当前交付约束。拆分源码前必须先建立可靠的合并产物流程，并证明安装命令、自更新和测试仍针对同一份发布脚本。

## 依赖方向与当前例外

维护时优先保持以下方向：

```text
菜单与入口
  -> 操作编排函数
    -> 节点 / 系统 / 防火墙 / 检测等领域函数
      -> 平台适配与核心运行时
```

这不是强制隔离层。当前经过设计的主要交叉调用包括：

- 启动更新探测在发现新版本后会调用自更新发布与回滚事务。
- 节点创建、重建、删除及 SSH 端口修改会调用防火墙过渡或对账接口，降低端口变化导致失联的风险。
- 防火墙会读取 SSH、节点、Docker 和公网监听信息，以计算完整放行集合。
- SSH 端口修改或恢复会在 Fail2ban 已安装时尝试同步其 jail 配置；同步失败只告警，不回滚已经完成的 SSH 核心修改或恢复。
- `cleanup_vpsbox_runtime` 是跨领域生命周期协调者。它在调用各恢复入口前使用 `declare -F` 检查函数是否存在；正常完整执行时这些函数均已定义，该检查只是防御性降级，不构成按需加载机制。

新增依赖前，应先确认能否复用现有的窄接口；不要让底层解析或平台函数反向调用菜单函数。这里描述的是依赖方向，不表示当前已经定义正式的公共 API。

## 全局状态所有权

Shell 没有模块级私有变量，所有权依靠命名、注释和调用约定维护。

| 状态 | 所有者与生命周期 |
|---|---|
| 固定版本、受管路径、超时和检测参数 | 加载时确定，业务函数只读 |
| `OS`、`OS_ID`、`OS_ID_LIKE` | `detect_os` 每次调用时刷新且只发布这三个字段；从 `/etc/os-release` 读取的中间字段保持局部，供启动流程及相关平台适配操作读取 |
| `METHOD` | 文件头提供 Shadowsocks 默认加密方法，节点状态加载会更新最近成功加载状态的 `METHOD` 字段 |
| `SSH_TARGET_PORT` | 文件头提供默认值，表示当前进程中本次 SSH 修改的目标端口；`sshd` 配置端口由 `sshd -T` 解析，真实监听还需结合 socket unit 与监听检测 |
| `ACTIVE_BOUNDED_*` | 限时命令执行器写入，统一清理函数回收子进程和计时器 |
| `LOCK_*` | 实例锁获取与退出清理流程维护 |
| `ACTIVE_NODE_*` | 节点事务的进程内句柄；清空时机取决于提交、回滚路径和失败阶段；未提交且已发生修改时，磁盘事务是后续恢复依据，已提交的残留目录只待清理 |
| `ACTIVE_FIREWALL_*`、`ACTIVE_SSH_FIREWALL_TRANSITION` | 防火墙临时应用、watchdog 和 SSH 联动流程维护 |
| `ACTIVE_UNAPPLIED_SSH_TRACKING` | SSH 修改事务维护，用于退出时处理尚未应用的跟踪状态 |
| `ACTIVE_FAIL2BAN_*` | Fail2ban 真实封禁测试维护，保存当前测试或上一次解封失败后尚未清理的临时状态 |
| `ACTIVE_SINGBOX_UPDATE_*` | sing-box 二进制更新事务的进程内句柄；回滚时先清空以避免重复进入，恢复失败时磁盘事务继续作为后续恢复依据 |
| `REMOTE_VERSION`、`UPDATE_AVAILABLE` | vpsbox 启动更新检查及自动、手动更新流程共同维护 |
| `PENDING_VPSBOX_UPDATE_*`、`VPSBOX_UPDATE_STARTUP_CONFIRMED`、`VPSBOX_UPDATE_WATCHDOG_*` | vpsbox 自更新 watchdog 和新进程启动握手维护 |
| `FW_*` | 防火墙加载、探测、解析和计算流程共同维护的单次操作状态；只有完整采集成功后才构成可消费快照。采集中途失败可能留下部分新值或上一轮值，调用者必须依据返回状态丢弃结果，且不得跨操作缓存 |
| 节点字段全局变量 | `load_state_file` 的短生命周期输出，表示最近一次成功加载的协议状态 |

`load_state_file` 成功后会覆盖 `DOMAIN`、`NAME`、`PORT`、`PASSWORD`、`METHOD`、`PROTOCOL`、`UUID`、`FLOW`、Reality 相关字段、`FINGERPRINT` 和 `CONFIG_ID`。调用者若需要跨越下一次成功加载保留值，必须先复制到局部变量；加载失败会保留上一次成功值。

## 函数接口约定

- 判断函数主要用退出状态表达真假；不要把其诊断文本当作返回值解析。
- 取值函数将数据写到标准输出，诊断信息应写到标准错误或由调用者显示。
- 核心事务或安全关键的主要状态未完整完成、且未完整恢复时返回非零。核心状态已经提交后，提交后清理或 Fail2ban 同步等 best-effort 辅助步骤失败时可以只告警并返回成功；新增此类例外必须就近写明。
- 垃圾清理等 best-effort 维护操作会逐项显示失败警告，但在其余步骤完成后可能返回成功。
- 少数加载器和采集器会写入已明确记录的全局状态，例如 `load_state_file` 和防火墙 `FW_*` 采集流程。新增此类接口时必须就近说明输出字段与失效时机。
- 菜单通过 `run_menu_action` 隔离单次操作失败；领域函数仍需保留准确的返回状态。

## 事务与恢复边界

不同领域的恢复目标不同，当前保持独立实现：

- 节点事务保护配置、状态、URI、sing-box 的 systemd/OpenRC 服务定义，以及服务启用和运行状态；未提交且已修改的事务可在下次启动恢复，已提交的残留事务只做清理。
- sing-box 更新事务保护旧二进制、可用时保存旧版本回滚包，并记录服务状态。
- vpsbox 自更新使用 `.previous`、watchdog 与新进程启动确认，降低替换后无法进入菜单的风险。
- 完整的 `[1] 一键开启/更新防火墙` 流程保存持久回滚快照，二次确认前只临时应用内核规则；未确认时由当前流程或独立 watchdog 尝试回滚，残留快照会在下一次防火墙操作前处理。配置同步和端口过渡使用各自的备份或对账路径，不属于该 watchdog 流程。
- SSH 端口修改和恢复使用持久快照及防火墙过渡，验证生效配置与目标端口监听后才收敛状态；SSH 基础加固使用持久恢复基线，但不进入防火墙过渡，只验证加固配置和原端口仍在监听。
- 纳入 `/etc/vpsbox/changes.env` 与备份框架的系统配置改动支持查看和恢复；系统升级、垃圾清理不进入该框架。SSH 的可恢复基线也记录在该框架内，但其修改和恢复另有 SSH 专用快照、验证及防火墙过渡规则。

不要仅因为这些流程都叫“事务”就合并它们。任何统一前都要分别覆盖中断、恢复失败、重复进入和旧版本状态。

## 生成模板边界

脚本内的 heredoc 既用于界面文本，也用于生成配置和辅助脚本。以下生成模板已用 `BEGIN GENERATED TEMPLATE` / `END GENERATED TEMPLATE` 标记：

- Shadowsocks 与 VLESS Reality 的节点 JSON；
- sing-box 的 systemd unit 与 OpenRC service；
- Fail2ban sshd jail、chrony 源、systemd-resolved DNS drop-in、SSH drop-in 与 BBR/fq sysctl drop-in；
- vpsbox 防火墙的 nftables 配置、systemd unit 与 OpenRC service；
- 防火墙独立回滚脚本；
- journald drop-in。

模板内部看似 Shell 函数的内容可能属于生成文件，而不是 `vpsbox.sh` 的顶层函数。插入章节、重命名函数或做机械重排时，必须先确认 heredoc 边界。

## 验证边界

本地改动至少运行：

```bash
( for file in vpsbox.sh tests/*.sh; do bash -n "$file" || exit 1; done )
shellcheck -S warning vpsbox.sh tests/*.sh
bash tests/run.sh
git diff --check
git diff --cached --check
```

正式发布验收应在具备所需 Linux 能力的环境运行
`VPSBOX_TEST_STRICT=1 bash tests/run.sh`，任何 SKIP 都会使验收失败；普通
`bash tests/run.sh` 会在末尾汇总跳过数量，适合日常回归，但有跳过时不等同于完整验收。

`git diff --check` 和 `git diff --cached --check` 不检查未跟踪文件；发布脚本会拒绝普通未跟踪文件，因此准备发布的新增文件应先纳入 Git。发布脚本也会拒绝已暂存和未暂存改动同时存在，并拒绝任何跟踪文件使用 `assume-unchanged`、`skip-worktree` 或异常索引状态；`vpsbox.sh` 还必须保持普通文件索引类型。检查期间会保持 `vpsbox.sh` 可读但禁止其他进程写入。使用 `-Bump` 时，脚本先检查当前内容，全部通过后才修改版本号；检查前后会核对 HEAD、暂存区和工作树状态，期间发生变化就安全停止。改号后会复验 `vpsbox.sh`；改号或复验失败时，只要当前进程仍持有写锁，就尝试通过同一文件句柄恢复并校验原始内容。执行前应让所有改动统一处于已暂存或未暂存状态；若检查前已全部暂存，改号后还需重新暂存 `vpsbox.sh`。统一暂存最终内容后，再无参数运行一次发布检查。不使用 `-Bump` 时，也可在全部改动已暂存、工作树无额外修改且版本已经正确的状态运行，避免工作树检查结果与待提交内容不一致。完整测试数量会随功能变化，不应把固定计数写入发布逻辑。涉及 `/proc`、所有权、后台进程、`flock` 或服务管理器语义时，应在 WSL 或 Linux 环境补充验证；静态检查和命令替身测试不能替代真实 VPS 上的服务验证。

准备发布时在 Windows PowerShell 运行：

```powershell
.\tools\release.ps1
```

`tools/release.ps1` 保留 UTF-8 BOM，以兼容 Windows PowerShell 5.1 对含中文脚本的默认解码；格式化时不要移除。

需要按项目规则增加补丁版本时使用 `-Bump`。发布脚本负责版本、ShellCheck、逐文件 Bash 语法、Git 差异，以及针对常见私钥头和部分 GitHub Token 格式的有限敏感信息静默检查，但不运行 `tests/run.sh`，不能替代上面的完整回归测试。

## 改动纪律

- 可读性重构和行为修改分批进行，先建立边界与测试，再移动实现。
- 保持菜单文字、文件路径、默认值、退出状态和恢复行为，除非当前任务明确要求改变。
- 优先通过现有窄接口协作，不直接读写其他领域的临时全局状态。
- 结构改动后复核外部依赖、领域函数和入口替身仍覆盖预期对象，不在 `source` 阶段执行系统操作。
- 本地整理不单独增加版本号；需要发布或推送时再按项目版本规则处理。
