# VPSBox 架构说明

本文面向 VPSBox 维护者，只记录稳定的模块边界、状态所有权和高风险流程。具体行为以 `vpsbox.sh` 为准，回归契约以 `tests/` 为准，发布规则以 `tools/release.ps1` 为准。

## 1. 交付形态

- `vpsbox.sh` 是唯一运行时源码，也是安装和自更新使用的发布产物。
- 脚本直接执行时进入 `vpsbox_main`；被测试 `source` 时只加载定义，不进入主程序。
- `tests/` 通过替换函数和外部命令验证行为，因此顶层不能新增系统修改、网络请求或服务操作。
- `tools/release.ps1` 只在仓库本地执行，不会随 `vpsbox.sh` 安装到 VPS。
- 当前保持单文件交付。若以后拆分源码，必须继续生成一份可独立运行、自更新和测试的 `vpsbox.sh`。

## 2. 源码职责

`vpsbox.sh` 内部按职责分区，但这些分区不是独立加载的模块。

| 区域 | 主要职责 |
|---|---|
| 核心运行时 | 输出与输入、确认、限时命令、进程清理、单实例锁 |
| 平台与持久化 | 系统识别、依赖管理、下载校验、原子文件操作、改动记录 |
| 节点与 sing-box | 节点状态、配置、服务、URI、事务及 sing-box 更新 |
| vpsbox 自更新 | 下载、替换、旧版恢复、watchdog 和新版启动确认 |
| 系统与安全 | BBR、IPv6、DNS、NTP、SSH、Fail2ban、主机名和系统维护 |
| 主机防火墙 | 端口采集、nftables 规则、Docker 端口、应用与回滚 |
| 检测与维护 | 一键检测、状态摘要、卸载和系统改动恢复 |
| 菜单与入口 | 菜单显示、动作分发和启动流程 |

常规调用方向为：

```text
入口与菜单
  -> 操作编排
    -> 节点 / 系统 / 防火墙等领域逻辑
      -> 平台适配与核心运行时
```

底层解析和平台函数不应反向调用菜单。允许的跨领域协作应通过窄接口完成，当前主要包括：

- 节点和 SSH 端口变更调用防火墙的端口过渡或完整对账；
- 防火墙读取 SSH、节点、Docker 和公网监听信息计算放行集合；
- SSH 端口变更在 Fail2ban 已安装时同步其 SSH jail；
- 启动流程协调未完成事务、自安装、自更新和菜单；
- 统一退出清理只负责调用各领域已有的清理或恢复入口。

## 3. 状态与持久数据

### 进程内状态

进程内全局变量分为四类：

- 加载期配置：版本、路径、超时和默认值，业务函数通常只读；
- 操作句柄：当前限时命令、实例锁和各类活动事务，由对应领域创建和清理；
- 采集快照：例如防火墙端口集合，只在一次完整采集成功后有效，不得跨操作缓存；
- 短期解析结果：例如节点状态字段，需要跨越下一次加载时应先复制到局部变量。

领域函数应使用返回状态表达成功或失败。取值函数通过标准输出返回数据，诊断信息不应混入可解析输出。

### 持久数据

| 数据 | 作用 |
|---|---|
| `/etc/sing-box/vpsbox.d/` 与对应状态文件 | 节点的权威配置和状态 |
| 节点 URI 文件 | 可从权威状态重建的派生缓存 |
| `/etc/vpsbox/install.env` | 首次安装版本与时间 |
| `/etc/vpsbox/changes.env`、`backups/` | 可持久恢复的系统改动及原始文件，不记录主机名修改 |
| `/etc/vpsbox/node-transaction/` | 节点事务 |
| `/etc/vpsbox/singbox-update/` | sing-box 更新事务 |
| `/etc/vpsbox/firewall*` | 防火墙配置和状态，以及操作需要时按需创建的回滚资料 |
| `/etc/sysctl.d/99-vpsbox-disable-ipv6.conf` | 用户明确确认后写入的 IPv6 永久禁用配置 |
| `/run/vpsbox/` | 当前启动期的锁和进程元数据，不作为业务恢复依据 |

系统实际配置仍由 `/etc` 下相应服务文件决定；`/etc/vpsbox` 保存的是 VPSBox 的管理状态、恢复依据和必要元数据。

## 4. 事务与恢复

各事务保护的对象和提交条件不同，不应合并成一个通用“大事务”。

| 流程 | 保护对象 | 完成条件 |
|---|---|---|
| 节点创建、重建、删除 | 节点配置与状态、sing-box 服务定义及服务管理器的 active/enabled 状态 | 新状态校验通过并完成发布 |
| sing-box 更新 | 旧二进制、哈希和服务状态 | 新二进制、节点和服务均验收通过 |
| vpsbox 自更新 | 当前脚本、`.previous`、命令入口 | 新进程完成初始化并成功进入菜单 |
| 防火墙完整更新 | 当前规则、持久配置和服务状态 | 临时规则验证后由用户确认 |
| SSH 端口变更 | SSH 配置、监听状态和防火墙过渡 | 配置有效且目标端口真实监听 |
| 可持久恢复的系统配置修改 | 原始文件及项目状态 | 文件和必要运行状态均应用成功 |

共同原则：

- 需要跨操作恢复的流程在首次修改前建立可信的恢复基线；
- 文件通过安全临时路径生成并校验，再原子替换正式文件；
- 未完成事务在下次启动或下次相关操作时恢复；
- 恢复不完整时保留依据并返回失败，不把残留清理当成恢复成功；
- 已提交事务遗留的目录只做清理，不回滚已完成状态；
- 完整防火墙更新和自更新使用独立 watchdog；普通低风险操作不套用同等级保护。

主机名修改不进入上述持久恢复体系。它只在单次操作中原子写入 `/etc/hostname` 和受管的 `/etc/hosts` 内容，并同步运行时主机名；任一步失败都返回非零，但 VPSBox 不为其保留跨操作备份，也不在“查看/恢复 vpsbox 系统改动”菜单中提供恢复入口。

禁用 IPv6 同样不进入通用系统改动恢复体系。操作只在检测到全局 IPv6 地址时展示接口与 CIDR，并以默认确认的 `[Y/n]` 询问；当前 SSH 会话明确使用 IPv6 时拒绝执行。确认后先对同目录临时 sysctl 配置应用并核验，再原子发布 `/etc/sysctl.d/99-vpsbox-disable-ipv6.conf`，不重启主机、网络服务或 sing-box。失败时只尽力恢复本次记录的 `all`、`default`、`lo` 三个运行参数；已经中断的 IPv6 连接以及删除的地址和路由不保证立即恢复。

上述专用配置不会显示在“查看/恢复 vpsbox 系统改动”中，卸载 VPSBox 时也不会自动删除，因此成功禁用后会跨重启并在卸载 VPSBox 后继续生效。已有 sing-box 节点配置不会被本操作改写；禁用后新建或重建节点会按当前系统能力选择 IPv4 监听。

## 5. 节点与 sing-box 模型

- VPSBox 最多管理一个 VLESS Reality 节点和一个 Shadowsocks 节点，两者可以同时存在。
- 每个协议拥有独立配置和状态，由同一个 sing-box 服务通过配置目录统一加载。
- 配置与状态文件是权威数据；URI 只负责展示和复制，不应阻止核心操作，陈旧时可重新生成。
- 节点创建或重建成功不以 URI 缓存写入成功为条件；核心提交后尽力重建 URI，失败时只警告。
- 完整性检查关注文件安全、协议、端口和关键凭据是否一致。
- `0.0.0.0` / `::` 监听和 `direct` 出站属于 VPSBox 当前生成模板，不是 sing-box 的通用规范。用户改成其他合法配置时应提示“已偏离 VPSBox 管理模板”，而不是直接判定为损坏。
- VLESS 配置保留受管凭据但增加额外用户或 Reality Short ID 时，核心完整性仍可通过，但模板状态必须标记为“已偏离 VPSBox 管理模板”。
- 一个协议损坏时，另一个健康协议仍可显示和使用；删除损坏节点只放宽目标协议的内容校验，不放宽固定路径、文件类型和写权限要求。
- 节点配置目录应由 root 管理且不可被其他用户写入；受管文件接受安全的只读或读写权限。
- 节点事务以服务管理器报告的 active/enabled 状态作为恢复依据，不以进程是否正在加载 VPSBox 配置目录代替 active 状态。
- sing-box 更新必须先验证当前受管节点，更新失败时恢复旧二进制和原服务状态。

## 6. 防火墙与 SSH/Fail2ban

VPSBox 的 nftables 防火墙是可选功能。VPS 厂商已有安全组时可以不启用，节点、SSH、Fail2ban 和其他系统功能不应因此失效。

启用后，VPSBox 只管理入站和转发所需规则，不创建 `output` 链。完整放行集合来自：

- 当前 SSH 端口；
- 已创建的节点端口；
- Docker 已发布端口；
- 当前公网监听端口；
- 用户手动维护的额外端口；
- DHCP 等必要的受限例外。

Docker 发布端口保留专用采集，因为部分 DNAT 映射不会表现为普通宿主机监听。采集结果不完整或 Docker 处于无法判断的活动状态时，不应用可能遗漏端口的规则。

防火墙回滚目录只在受管防火墙已启用且当前操作确实需要配置备份或 watchdog 时按需创建。防火墙未启用时，节点和 SSH 操作不应仅因状态检查创建空目录；已启用防火墙执行端口同步时若目录缺失，则先安全建立回滚目录再继续。

SSH 端口修改遵循“先保留访问路径、再验证新端口、最后收敛旧状态”的顺序。UFW 或 firewalld 已启用但无法自动证明放行时，脚本提示风险并交由用户明确确认。

Fail2ban 的硬验收包括配置、服务、jail、SSH 端口和 nftables action 一致性。原本停止的 Fail2ban 可在同步期间临时启动以完成运行态验收；正常完成后恢复原停止状态，基础验收完成前同步被中断时，退出清理会尽力恢复同步前的配置与运行状态。实际封禁再解封属于深度检测，失败只警告，不推翻已经通过的基础配置。

## 7. 启动流程

直接执行脚本时，入口按以下顺序运行：

```text
安装自更新失败保护
  -> 检查 root 权限并识别系统
  -> 获取单实例锁
  -> 恢复未完成的 sing-box 更新
  -> 恢复未完成的节点事务
  -> 修复可重建的节点 URI 缓存
  -> 安装或刷新 vpsbox 命令入口
  -> 普通启动时检查并应用 vpsbox 更新
  -> 进入菜单
  -> 确认新版进程已成功启动
```

sing-box 更新或节点事务无法恢复时应停止启动，避免新操作覆盖现有恢复依据。菜单动作通过统一分发隔离单次失败，失败后保留菜单，同时让领域函数的真实退出状态可被测试和日志观察。

## 8. 维护与验证

修改时遵循以下边界：

- 保持菜单文字、持久路径、默认值和恢复语义，除非当前任务明确要求改变；
- 行为修改同步更新相关测试，纯重构不改变外部行为；
- 不在脚本被 `source` 时执行系统操作；
- 生成配置或辅助脚本前先确认 heredoc 边界，避免把模板内容当成顶层函数；
- 本地整理不单独增加版本号；发布或推送时再按项目版本规则处理。

验证强度与改动范围相称：

```bash
# Shell 改动
bash -n vpsbox.sh
shellcheck -S warning vpsbox.sh

# 相关或完整回归
bash tests/run.sh

# 严格发布验收
VPSBOX_TEST_STRICT=1 bash tests/run.sh

# 差异检查
git diff --check
```

只修改文档时复核最终差异并运行 `git diff --check` 即可。涉及 Linux 权限、`/proc`、服务管理器、真实防火墙或 SSH 连通性的行为，在本机测试无法覆盖时再使用隔离 Linux 环境或已明确授权的 VPS。

正式发布前在 Windows PowerShell 运行：

```powershell
.\tools\release.ps1
```

版本同步、仓库状态和发布文件检查由该工具负责，具体实现不在本文重复维护。
